# Internationalization

> **Status:** foundation in place (#498). The routing, the locale negotiation, the language switcher and the message files work for every page. Most interface strings are still hard-coded in English: they are moved to the message files by the extraction issues of the bilingual interface, following the pattern below. Hreflang alternates in the page metadata and per-locale sitemap entries are not built yet (#501).

The interface is built with [next-intl](https://next-intl.dev) 4. It covers routing, locale negotiation, translation in Server and Client Components, formatting and navigation; the project writes no equivalent of these.

## Locales and URLs

- Locales: `en` and `fr`. Default: `fr`, the stage-1 audience. Declared once in `i18n/routing.ts`.
- Every page lives under `app/[locale]/` and every page URL carries its locale prefix (`localePrefix: 'always'`): `/fr/browse`, `/en/parts/hinge-clip`.
- A page URL without a prefix answers a 307 redirect to the same path and query string with a prefix. The locale is negotiated by the next-intl middleware, in this order: the `NEXT_LOCALE` cookie, then the `Accept-Language` header, then `fr`. There is no IP geolocation.
- The `NEXT_LOCALE` cookie is set by the middleware on a page load whose locale differs from the cookie or from `Accept-Language`, and in the browser when the visitor uses the language switcher. It therefore holds the locale the visitor last used, and an unprefixed path resolves to that locale.
- A prefix that is not a locale is treated as part of the path: `/de/browse` redirects to `/fr/de/browse`, which answers 404.
- The middleware adds a `Link` response header listing the URL of the page in each locale, with `hreflang` (next-intl default).

Not localized, and excluded from the proxy matcher in `proxy.ts`: API routes (`/api/**`), the email confirmation callback (`/confirm`, `app/(auth)/confirm/route.ts`), Next.js internals and every path with a file extension (`/robots.txt`, `/sitemap.xml`, images). API routes and `/confirm` refresh the Supabase session through the server client (`lib/supabase/server.ts`), which can write cookies in a route handler.

## Request pipeline

`proxy.ts` calls `updateSession` (`lib/supabase/middleware.ts`) with the next-intl middleware:

1. The Supabase session is refreshed. Refreshed cookies are written to the request before the locale routing runs, so Server Components of the same request read the new session, and to the response, so the browser stores them.
2. A protected route is checked on its prefixed path (see [AUTH_FLOW.md](./AUTH_FLOW.md#protected-routes)). A signed-out request is redirected to the login page of the same locale.
3. Otherwise the next-intl middleware redirects an unprefixed URL, or passes a prefixed one through with its locale.

When the public Supabase variables are not set, step 1 and 2 are skipped and the locale routing still runs.

## Layouts and not-found pages

- `app/[locale]/layout.tsx` is the document root: `<html lang>`, fonts, global styles, the default metadata and `NextIntlClientProvider`. It answers 404 for a locale segment that is not a locale. It sits under `[locale]` so that switching language, which changes this segment, renders `<html lang>` and the messages sent to Client Components again; a layout above the segment would keep the previous language after a client-side navigation.
- `app/layout.tsx` only passes its children through. It exists because `app/not-found.tsx` needs a root layout.
- `app/[locale]/[...rest]/page.tsx` calls `notFound()`, so an unknown path under a locale renders `app/[locale]/not-found.tsx` in that locale, with status 404.
- `app/not-found.tsx` renders its own minimal document for unmatched URLs outside the localized pages, such as an unknown `/api/` path.
- Server Components read the locale from a request header set by the middleware, which opts pages into dynamic rendering. Every page was already rendered dynamically, since the navbar reads the session, so `setRequestLocale` is not used.

## Active locale

The active locale is read with next-intl's own functions, without a wrapper:

- `getLocale()` from `next-intl/server` in Server Components, route-level metadata and Server Actions;
- `useLocale()` from `next-intl` in Client Components.

Both return the locale resolved by `i18n/request.ts`: the locale of the URL prefix, or `fr` when it is missing or unknown. `i18n/request.test.ts` covers this resolution.

The region used for regional product names is a separate setting (#465). Until #465 ships, it is still read from `Accept-Language` by `parseAcceptLanguage()` (`lib/utils/locale.ts`), on the product page, in `/api/product-references` and for the `locale` column of `search_misses`. The interface locale carries no region, so it does not replace that parser; #465 uses `getLocale()` or `useLocale()` as the default of its region setting.

## Navigation

- Internal links and navigations use `Link`, `redirect`, `usePathname` and `useRouter` from `@/i18n/navigation` (created with `createNavigation(routing)`), never their `next/link` or `next/navigation` equivalents. They add the current locale prefix to an unprefixed internal path: `<Link href="/browse">` renders `/fr/browse` on a French page. `usePathname` returns the path without the prefix.
- `redirect` takes the locale explicitly: `redirect({ href: '/login', locale: await getLocale() })`.
- `notFound()` and `useSearchParams()` do not depend on the locale and stay imported from `next/navigation`.
- A URL written as a string for a full page load stays unprefixed: `window.location` assignments, the links in Supabase Auth emails (`/confirm`, `/update-password`) and the redirects of `app/(auth)/confirm/route.ts`. The proxy redirects them to the visitor's locale through the cookie, and the redirect URLs allowed in the Supabase Auth settings do not change.
- The `redirect` query parameter of the login and sign-up pages holds the browser path, prefix included (`/login?redirect=%2Fen%2Fpublish`).

## Messages

- One file per locale: `messages/en.json` is the source, `messages/fr.json` the French translation. `i18n/request.ts` loads the file of the active locale; `NextIntlClientProvider` passes the messages to Client Components (next-intl default).
- Keys are grouped in namespaces named after the page or component that uses them (`Navbar`, `NotFound`). A string shared by several components belongs to the namespace of the component that owns it, which the others read (`MobileMenu` reads `Navbar`).
- `i18n/app-config.d.ts` declares the locales and the shape of `messages/en.json` to next-intl (`AppConfig`): a missing or misspelled key, or a namespace that does not exist, fails `tsc`. `i18n/request.test.ts` fails when `messages/fr.json` lacks a key of `messages/en.json` or has one it does not.
- Product and brand names are not translated. Part descriptions stay in the language they were written in.

### Reference pattern

| Case | Example |
|---|---|
| Server Component | `components/layout/navbar.tsx`: `const t = await getTranslations('Navbar')` |
| Client Component | `components/layout/mobile-menu.tsx`: `const t = useTranslations('Navbar')` |
| Page metadata | `app/[locale]/layout.tsx`: `generateMetadata` with `getTranslations('Metadata')` |
| Not-found page | `app/[locale]/not-found.tsx` |
| ICU argument | `LanguageSwitcher.localeName`: `{locale, select, en {English} fr {Français} other {{locale}}}` |

Extracted so far: `Metadata`, `Navbar`, `LanguageSwitcher`, `NotFound`. An extraction adds each key to both message files in the same pull request.

## Language switcher

`components/layout/language-switcher.tsx`, in the navbar at every breakpoint, renders one link per other locale, labelled with the name of that language in that language (`English`, `Français`), shortened to its code (`EN`, `FR`) below the `md` breakpoint so the navbar stays on one line, with the full name as accessible name. The link is marked with `lang` and `hrefLang`. The link is next-intl's `Link` with its `locale` prop: it points to the current path and query string in the other locale, and sets the locale cookie on click. A URL fragment is not carried. The component reads `useSearchParams()`, so the navbar renders it inside `<Suspense>`.
