# Internationalization

> **Status:** foundation in place (#498). The public pages, the not-found and error pages and the shared components are available in English and French (#499), as are the auth and dashboard pages, the publish tool, and the messages of the API routes and Server Actions (#500). The legal pages are available in both languages, French prevailing (#504); the French texts are a draft until their human review is recorded in the pull request. Category names are translated in the database (#502). Canonical URLs, structured data and the sitemap carry the locale (#501).

The interface is built with [next-intl](https://next-intl.dev) 4. It covers routing, locale negotiation, translation in Server and Client Components, formatting and navigation; the project writes no equivalent of these.

## Locales and URLs

- Locales: `en` and `fr`. Default: `en`, for international reach; French is served through locale negotiation. Declared once in `i18n/routing.ts`.
- Every page lives under `app/[locale]/` and every page URL carries its locale prefix (`localePrefix: 'always'`): `/fr/browse`, `/en/parts/hinge-clip`.
- A page URL without a prefix answers a 307 redirect to the same path and query string with a prefix. The locale is negotiated by the next-intl middleware, in this order: the `NEXT_LOCALE` cookie, then the `Accept-Language` header, then `en`. There is no IP geolocation.
- The `NEXT_LOCALE` cookie is set by the middleware on a page load whose locale differs from the cookie or from `Accept-Language`, and in the browser when the visitor uses the language switcher. It therefore holds the locale the visitor last used, and an unprefixed path resolves to that locale. It is a session cookie holding only the locale code, listed in section 5 of the privacy policy (`app/[locale]/(legal)/privacy/privacy.en.tsx` and `privacy.fr.tsx`).
- A prefix that is not a locale is treated as part of the path: `/de/browse` redirects to `/en/de/browse`, which answers 404.
- The middleware adds a `Link` response header listing the URL of the page in each locale, with `hreflang` (next-intl default). See [SEO URLs](#seo-urls).

Not localized, and excluded from the proxy matcher in `proxy.ts`: API routes (`/api/**`), the email confirmation callback (`/confirm`, `app/(auth)/confirm/route.ts`), Next.js internals and every path with a file extension (`/robots.txt`, `/sitemap.xml`, images). API routes and `/confirm` refresh the Supabase session through the server client (`lib/supabase/server.ts`), which can write cookies in a route handler.

## Request pipeline

`proxy.ts` calls `updateSession` (`lib/supabase/middleware.ts`) with the next-intl middleware:

1. The Supabase session is refreshed. Refreshed cookies are written to the request before the locale routing runs, so Server Components of the same request read the new session, and to the response, so the browser stores them.
2. A protected route is checked on its prefixed path (see [AUTH_FLOW.md](./AUTH_FLOW.md#protected-routes)). A signed-out request is redirected to the login page of the same locale.
3. Otherwise the next-intl middleware redirects an unprefixed URL, or passes a prefixed one through with its locale.

When the public Supabase variables are not set, step 1 and 2 are skipped and the locale routing still runs.

## Layouts and not-found pages

- `app/[locale]/layout.tsx` is the document root: `<html lang>`, fonts, global styles, the default metadata and `NextIntlClientProvider`. It answers 404 for a locale segment that is not a locale. It sits under `[locale]` so that switching language, which changes this segment, renders `<html lang>` and the messages sent to Client Components again; a layout above the segment would keep the previous language after a client-side navigation.
- `app/layout.tsx` only passes its children through. It exists because `app/not-found.tsx` needs a root layout.
- `app/[locale]/[...rest]/page.tsx` calls `notFound()`, so an unknown path under a locale renders `app/[locale]/not-found.tsx` in that locale, with status 404.
- `app/not-found.tsx` renders its own minimal document for unmatched URLs outside the localized pages, such as an unknown `/api/` path.
- Server Components read the locale from a request header set by the middleware, which opts pages into dynamic rendering. Every page was already rendered dynamically, since the navbar reads the session, so `setRequestLocale` is not used.

## Active locale

The active locale is read with next-intl's own functions, without a wrapper:

- `getLocale()` from `next-intl/server` in Server Components, route-level metadata and Server Actions;
- `useLocale()` from `next-intl` in Client Components.

Both return the locale resolved by `i18n/request.ts`: the locale of the URL prefix, or `fr` when it is missing or unknown. `i18n/request.test.ts` covers this resolution.

The region used for regional product names is a separate setting (#465). Until #465 ships, it is still read from `Accept-Language` by `parseAcceptLanguage()` (`lib/utils/locale.ts`), on the product page, in `/api/product-references` and for the `locale` column of `search_misses`. The interface locale carries no region, so it does not replace that parser; #465 uses `getLocale()` or `useLocale()` as the default of its region setting.

## Navigation

- Internal links and navigations use `Link`, `redirect`, `usePathname` and `useRouter` from `@/i18n/navigation` (created with `createNavigation(routing)`), never their `next/link` or `next/navigation` equivalents. They add the current locale prefix to an unprefixed internal path: `<Link href="/browse">` renders `/fr/browse` on a French page. `usePathname` returns the path without the prefix.
- `getPathname({ href, locale })` returns the prefixed path of an in-app path in a given locale, for URLs written outside a link (canonical URLs, structured data, sitemap). No code concatenates `/${locale}` by hand.
- `redirect` takes the locale explicitly: `redirect({ href: '/login', locale: await getLocale() })`.
- `notFound()` and `useSearchParams()` do not depend on the locale and stay imported from `next/navigation`.
- A URL written as a string for a full page load stays unprefixed: `window.location` assignments, the links in Supabase Auth emails (`/confirm`, `/update-password`) and the redirects of `app/(auth)/confirm/route.ts`. The proxy redirects them to the visitor's locale through the cookie, and the redirect URLs allowed in the Supabase Auth settings do not change.
- The `redirect` query parameter of the login and sign-up pages holds the browser path, prefix included (`/login?redirect=%2Fen%2Fpublish`).

## Messages

- One file per locale: `messages/en.json` is the source, `messages/fr.json` the French translation. `i18n/request.ts` loads the file of the active locale; `NextIntlClientProvider` passes the messages to Client Components (next-intl default).
- Keys are grouped in namespaces named after the page or component that uses them (`Navbar`, `NotFound`). A string shared by several components belongs to the namespace of the component that owns it, which the others read (`MobileMenu` reads `Navbar`).
- `i18n/app-config.d.ts` declares the locales and the shape of `messages/en.json` to next-intl (`AppConfig`): a missing or misspelled key, or a namespace that does not exist, fails `tsc`. `i18n/request.test.ts` fails when `messages/fr.json` lacks a key of `messages/en.json` or has one it does not.
- Product and brand names are not translated. Part descriptions stay in the language they were written in.
- Category names are data, not messages: see [Category names](#category-names).

### Reference pattern

| Case | Example |
|---|---|
| Server Component | `components/layout/navbar.tsx`: `const t = await getTranslations('Navbar')` |
| Client Component | `components/layout/mobile-menu.tsx`: `const t = useTranslations('Navbar')` |
| Page metadata | `app/[locale]/layout.tsx`: `generateMetadata` with `getTranslations('Metadata')` |
| Not-found page | `app/[locale]/not-found.tsx` |
| ICU argument | `LanguageSwitcher.localeName`: `{locale, select, en {English} fr {Français} other {{locale}}}` |

A component used in several places owns its strings: `SearchBar` translates its own placeholder (one per mode), submit button and clear button, so its callers pass none. An extraction adds each key to both message files in the same pull request.

Covered: every page of `app/[locale]/` and every component. The legal pages are written per locale (see [Legal pages](#legal-pages)). Other conventions:

- **Counts** shared by many components (`3 parts`, `1 product`) are the ICU plurals of the `Counts` namespace, read by every component that shows one.
- **Rich text**: a sentence with a link or emphasis inside is one message with tags, rendered with `t.rich` (`CategoryPage.inlined`, `Footer.licenses`, the `ContributingPage` messages). The sentence is never split into fragments around the element.
- **Page metadata**: titles and descriptions are built in `generateMetadata` from the messages of the page or of the `Seo` namespace. `lib/utils/seo.ts` holds no copy: it provides the canonical paths, the localized URLs (see [SEO URLs](#seo-urls)), the JSON-LD builders, the names they are built from (`partFitLabel`, `productFullName`, `rootBreadcrumbTrail`) and the snippet length cut (`seoDescription`).
- **Labels of stored values** (evidence levels, publication kinds, print report results, sort options, feedback types, search miss outcomes, reference types) are messages keyed by the value; the code keeps only the value and its styling (`describePublication` returns the kind, `EvidenceLevelBadge` reads `EvidenceLevel.<level>`).
- **Definitions in `lib/`** shared by the interface and a server gate keep only their keys, and their wording is the messages keyed by them: the curation criteria and flags (`CURATION_BLOCKING_CRITERIA`, `CURATION_FLAGS` → `CurationCriteria`, `CurationFlags`), the publish steps and tracks (`PUBLISH_STEP_NAMES`, `PUBLISH_TRACKS` → `PublishSteps`, `PublishTracks`), the clauses of the originality declaration (`ATTESTATION_CLAUSES` → `Attestation.clauses`) and the local publish blockers, which carry a `reason` read from `PublishBlockers`.
- **Errors raised in the browser** are typed rather than worded where the interface names something: `StorageUploadError` (`lib/storage/client-upload.ts`) carries the file name, and Supabase Auth errors are shown by their code (see [Auth errors and emails](#auth-errors-and-emails)).
- Strings the code receives from an API route or a Server Action (validation, download and publish errors, the publish gates' `blockers`) are displayed as received: they are already in the locale of the page (see [API and validation messages](#api-and-validation-messages)).
- **Guard:** `npm run lint` runs the `react/jsx-no-literals` rule of `eslint-plugin-react` on `app/**/*.tsx` and `components/**/*.tsx`, except the legal content components (`*.en.tsx`, `*.fr.tsx`). JSX text may only be one of the punctuation marks and symbols listed in `eslint.config.mjs`. The rule checks JSX text, not attribute values: a `placeholder`, `aria-label` or `alt` is reviewed like any other string. A proper noun that is not translated (the wordmark of `components/layout/logo.tsx`) is a named constant.

## SEO URLs

- **hreflang**: declared once, in the `Link` response header the next-intl middleware sends on every page (`alternateLinks`, on by default). It lists the absolute URL of the page in `en` and `fr`, plus `x-default`, without the query string. `lib/supabase/middleware.ts` returns the response of the locale routing with the refreshed session cookies added, so the header reaches the browser. No page declares `alternates.languages` and the sitemap carries no alternates: one method is enough for search engines.
- **Canonical and Open Graph URLs**: every public page, the home, the contributing guide and the legal pages included, takes them from `localizedPageMetadata(path, locale, openGraph)` in `lib/utils/seo.ts`. It returns `alternates.canonical` and `openGraph`, the page's own Open Graph fields merged with `url`; no page writes `alternates` or `openGraph` itself. The URL is absolute and carries the active locale (`/fr/parts/hinge-clip`), and never the query string: paginated and filtered views share the canonical URL of the listing. `/search` has none: it is `noindex`.
- **Structured data**: `buildPartJsonLd` and `buildBreadcrumbJsonLd` take the locale, and every URL they write (`@id`, `url`, breadcrumb items) is localized. The visible breadcrumbs keep unprefixed paths, which `Link` prefixes.
- **Sitemap**: `/sitemap.xml` lists each path it covers (see [SEO.md](./SEO.md#sitemap-and-robots-257); the legal pages are not listed) once per locale of `routing.locales`, each entry with its localized absolute URL and its `lastModified` (`buildSitemap` in `lib/utils/sitemap.ts`). The 50,000-URL limit applies to the total number of entries; a path keeps all its locales or none.
- Each localized URL is `localizedUrl(path, locale)`: `getPathname` from `@/i18n/navigation`, made absolute with `absoluteAppUrl`.

## API and validation messages

API routes are outside the locale routing, so a route resolves the locale of the page that called it with `requestLocale(request)` (`lib/utils/locale.ts`). It applies the rule of the next-intl middleware: the `NEXT_LOCALE` cookie, else the most preferred supported language of `Accept-Language`, else the default locale. The middleware sets the cookie whenever a page's locale differs from what `Accept-Language` negotiates, so the result is the locale of the calling page. Server Actions run under the page's locale and read it with `getLocale()`.

- **Route messages** are the `Api` namespace, read with `getApiTranslations(request)` (`lib/api/translations.ts`), a `getTranslations` call with the request locale. Every error a route answers, the `skipped` and `warning` notes the publish tool shows, and the `blockers` of the two publish gates (`Api.blockers`) are messages. A query function that reports a refusal returns the `Api` key, which the route translates: `validateSourceUrlMatchesPlatform` and `findProductLinkBlocker`. Server Actions read the same namespace with `getTranslations('Api')`.
- **Validation messages** are built by `lib/api/parse.ts` with Zod's own locale (`z.locales.fr()`, `z.locales.en()`): Zod's default message, after the label of the field in the `Fields` namespace (`Unité : Option invalide : une valeur parmi "mm"|"cm"|"in" attendue`). A nested field joins its labels with ` › `; a field without a label is named as in the request. A field missing where one is expected reads `Required`. A schema writes its own message only when the default would not say what to fix, and writes it as a key of the `Validation` namespace (`{ error: 'httpUrl' }`); a custom issue passes the message's arguments as `params`. `parseJsonBody(request, schema)` and `parseSearchParams(request, schema)` resolve the request locale; `validate(schema, input)` uses `getLocale()`.

## Auth errors and emails

- Supabase Auth answers in English. The auth forms show the `AuthErrors` message of the error's `code`, through `authErrorKey()` (`lib/utils/auth-errors.ts`), and a generic message for any other. A username already taken is reported with the code `username_taken`.
- The email confirmation callback (`app/(auth)/confirm/route.ts`) redirects a failed or malformed link to `/error?error=confirmation` (`CONFIRMATION_ERROR`), and the error page explains it in the locale of the page; the error text of Supabase is not shown.
- The authentication emails are rendered by the templates of the Supabase project, outside this repository. Sign-up stores the interface locale in the user metadata (`locale`, next to `username`), so a template can choose its language with `{{ if eq .Data.locale "fr" }}…{{ else }}…{{ end }}`, the `else` branch in English, the default locale. The templates themselves are edited in the Supabase dashboard. A user who signed up before #500 has no `locale` in their metadata and gets the `else` branch.

## Legal pages

The terms of use, the privacy policy and the legal notice (`app/[locale]/(legal)/`) are long-form texts reviewed as a whole, so they are written in TSX rather than in messages: one content component per locale next to each page (`terms.en.tsx`, `terms.fr.tsx`, and likewise for `privacy` and `legal-notice`). The content components hold plain markup (`section`, `h2`, `h3`, `p`, `ul`, `a`) with no class.

Each `page.tsx` passes its two components to `LegalPage` (`components/legal/legal-page.tsx`), which renders the one of the active locale (`getLocale()`) inside the shared shell: the title, the governing language clause and the styles of the section markup. `legalPageMetadata()` builds the title and description. The titles, descriptions and clause are the `LegalPages` messages.

The governing language clause, shown under the title of every legal page, states that the French version prevails in case of discrepancy, since Common Parts operates under French law. A change to a legal text is made in both content components in the same pull request. The anchor of section 4.2 of the terms (`TERMS_LICENSES_SECTION_ID` in `lib/utils/licenses.ts`) is the same in both locales, so the links to it only change prefix.

## Category names

Categories are named in the database (#502): `categories.name` is the English name, `categories.name_fr` the French one (nullable, never blank). On a French page a category shows its French name, and its English name when `name_fr` is null; on an English page, its English name. Slugs are the same in both locales, so a category URL differs only by its prefix (`/fr/categories/vacuum-cleaner`, `/en/categories/vacuum-cleaner`). The French names of the 140 categories are seeded by `supabase/migrations/20261106140715_category_names_fr.sql`; a category added later falls back to English until its `name_fr` is set.

The rule is applied where the name is read, never in a component:

- The navigation and search functions take a `p_locale` argument (`'en'` by default) and return every category name in that locale, through the database function `localized_name()`. Lists ordered by name (hub roots, subcategories, a brand's categories) are ordered by the localized name. The query functions pass `getLocale()`: `fetchBrowseNav`, `fetchCategoryPage`, `fetchBrandNav`, and `searchAll`, which takes the locale as an argument.
- The queries that embed a category through PostgREST select `name, name_fr` and name it with `localizeCategory()` (`lib/utils/locale.ts`): the product page, the part page metadata and breadcrumb, the brand listings and `fetchCategoriesTree`.
- API routes are not localized, so the Client Components that display a category read from an API route send their locale with `useLocale()`: `GET /api/search?locale=` (autocomplete), `GET /api/parts/[slug]/details?locale=` (part page) and `GET /api/categories?locale=` (publish form). The `locale` parameter is validated by `locale` in `lib/schemas/common.ts` and defaults to `en`, like the database functions, so a request that names no locale gets the English names it got before #502.

Search matches a category by its English and its French name whatever the locale of the page (see [SEARCH.md](./SEARCH.md)).

## Dates and numbers

Dates, relative times, numbers and units are formatted by next-intl in the active locale: `useFormatter()` in components, `getFormatter()` in Server Components (`format.dateTime`, `format.relativeTime` with `useNow()`, `format.number` with a `unit` style for file sizes and material weight). Counts inside a sentence use an ICU plural with `#`. `lib/utils/formatters.ts` holds no locale-dependent formatter, except `formatRegionName(code, locale)`, which names a region with `Intl.DisplayNames` since next-intl has no display-name formatter. No time zone is configured: dates are formatted in the server's time zone, which `NextIntlClientProvider` passes to Client Components.

## Language switcher

`components/layout/language-switcher.tsx`, in the navbar at every breakpoint, is a globe icon button labelled `Language` / `Langue` that opens a menu (`DropdownMenu` from `components/ui/`). The menu lists every locale of `routing.locales` as a radio item, labelled with the name of that language in that language (`English`, `Français`) and marked with `lang`; the active locale is checked. Choosing one calls next-intl's `router.replace` with its `locale` option: the current path and query string reopen in that locale, and the locale cookie is set. A URL fragment is not carried. A new locale appears in the menu once it is added to `routing.locales` and its message file exists. The component reads `useSearchParams()`, so the navbar renders it inside `<Suspense>`.
